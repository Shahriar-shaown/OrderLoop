# Known limitations and proposed fixes

Prioritised for a **controlled pilot**. Built from [../known-issues.md](../known-issues.md) and the limitation notes in
`docs/api.md`, `automation.md`, `couriers.md`, `finance.md`, `meta.md`, `mobile.md`, `dashboard.md` and `inventory.md`, plus gaps found
while writing the operations docs on 2026-10-21. The grouping into Blocker / Should fix / Later is a **proposal** for the pilot owner to
confirm. Sizes: **S** = hours to a day or two, **M** = a few days, **L** = a week or more.

Where a "Blocker" depends on pilot scope (for example live couriers or phone push), it says so: with that feature out of scope it
drops to "Should fix soon".

## Findings from the final review

Two independent read-only reviews (security, and order/inventory/finance correctness) were run on 2026-10-21 against the
working tree that included the automation and Meta code, followed by fixes and a re-run of the checks. This is what they found
and what became of it. "Fixed" means a change with a test; it does not mean the review was repeated by a second reviewer.

**Security review: gate FAIL before fixes (1 High, 4 Medium, 11 Low). Reported clean:** password hashing, JWT algorithm pinning,
per-request session/membership re-check, refresh rotation and reuse detection, forced RLS and the SECURITY DEFINER functions
(search_path pinned, grants minimal), webhook signature-before-parse, parameterised SQL, secrets in tracked files and history,
CSV formula-injection guard, web CSP.

**Found while verifying (not by the reviews):** the new `inventory:verify` checker sorted movements as text ("21" before "3") and
reported false drift on the dev database. Fixed and covered by a regression test that fails on the old query; the dev ledger now
verifies clean (8 stock levels, 21 movements).

**Also surfaced by the operations work:** backups must be taken by a superuser or `BYPASSRLS` role (a plain `pg_dump` as the owner
fails, and `--enable-row-security` silently omits tenant data: docs/operations/backup-and-restore.md); sign-up was open to anyone
(now `REGISTRATION_MODE=allowlist` is available: set it for the pilot); there is no account or customer deletion (a store
requirement, see section A); migration folders are stamped later than today's date, so new migrations must use later timestamps.

**Update (2026-10-21, deployment and operations work):** blockers B1, B2, B3, B5 and B7 and part of B4 have artifacts, tooling or code now, each **verified only on a developer laptop**; the rows in section A say precisely what was run and what was not.
Two things the work itself surfaced and fixed: the worker demanded the API's token-signing key and other API-only production settings (it validated the same schema), so a production worker could not start without being given the signing key;
and `redis-cli -u redis://:password@host` is refused by Redis 7, which would have left the backup-age metric silent.
